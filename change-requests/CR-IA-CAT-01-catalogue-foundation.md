## 1. Executive summary

This CR establishes the Information Asset catalogue as a **method, not as content**. It lands the dependency manifest, the pointer gates, the catalogue gates 1–3, the README contract, and the contributing rules. It admits **no records**.

It follows the methodology-first rule established for the business-capability catalogue and restated for the information-classes catalogue (`CR-IC-CAT-01`): the first increment of a catalogue establishes admission criteria, the evidence process, and the framework-overlay rules. Records come with `CR-IA-CAT-04`, gated on the schema CR (`CR-IA-CAT-02`) and the record documentation standard (`CR-IA-CAT-03`).

## 3. Methodology-first rationale

The Information Asset entity is normative in the metamodel with generated artifacts (JSON schema, pydantic, SQLite, TypeScript) already present, but lifecycle-`proposed`: no catalogue realization. A catalogue that admits records before its schema projection and record standard are ratified accumulates content it cannot govern: consumption forms drift, classification crosswalks assert without provenance, and the first population CR inherits a cleanup instead of a clean admission. This CR therefore lands the method first.

## 4. Allocation reconciliation

The repository's `metamodel-pointer.yaml` declares `dea:entity-information-asset` (alias `IA`) at L4 / `L4-information-knowledge`, exactly as the root model carries it at **v0.8.0** — the earliest pin choices among sibling catalogues (v0.2.x) predate the allocation, which enters the OpenDEAM model at v0.6.0. The `validate-allocation.yml` workflow validates the pointer against the pinned root-model ref; `scripts/check_pointer.py` asserts the same facts locally, so a pointer drift fails CI twice for the same reason: once against the root model, once on the declared fields.

The pointer is hybrid because the ecosystem has two pointer consumers: the regenerator (identity keys) and the allocation validator (`metamodel:` block). Sibling catalogues generated by the older fan-out satisfy only the latter; this catalogue's identity block makes the regenerator's catalog metadata derived rather than defaulted.

## 5. Dependencies

`dependencies.yaml` pins: metamodel `1.0.0` (hard), root model `v0.8.0` (allocation), metaframework `v2.6.0` (vendored toolchain), information-classes (crosswalk target) and business-capabilities (realization consumer, U-2 beneficiary) at `main`. Catalog pins move to tag pins at each target's first post-reset release cut, following the capabilities precedent.

2. `python3 scripts/check_pointer.py` → `Findings: 0`.
3. `python3 scripts/check_record_posture.py` → `Findings: 0` (0 records).
4. `python3 scripts/regenerate_catalog.py --check --schema catalog-index-schema/catalog-index-schema.json` → exit 0.
5. `python3 scripts/check_catalog_index.py --strict --schema catalog-index-schema/catalog-index-schema.json` → OK.
6. `validate-allocation.yml` passes against OpenDEAM v0.8.0 (verified locally with `validate_consumer.py`).
7. Authorship gate passes: no authorship-bearing field carries a non-allowlisted value.
8. `CATALOG.yaml` counts: entities 0, canonical 0.

## 9. NOT-list

1. No records are admitted by this CR.
2. No schema is declared or vendored by this CR (the metamodel schema is referenced, not copied, until CR-IA-CAT-02).
3. No changes to `dea-metamodel`, `dea-architecture-framework`, `dea-catalog-information-classes`, or `dea-governance` in this PR.
4. No local identity schemes beyond `dea:information-asset-<slug>` (the information-classes id precedent) are introduced.
5. No `dea:derived-from` lineage assertions until the data-entities catalogue is populated (capabilities U-1 precedent: absence is honest).
